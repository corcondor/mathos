# DeepSeek自身が進める継続目標

ユーザーの意図は、Codexの `/goal` を説明することではなく、DeepSeek自身に
課題選択から研究・証明生成・修正まで継続させること。
この実装は **DeepSeek用のカスタムスキルと実行器**であり、DeepSeek APIに
ネイティブの `/goal` コマンドがあるという意味ではない。

## 誰が判断するか

`deepseek-v4-1-flash-1017` が毎回JSONで次の行動を選ぶ。
資料・mathlibの読取と検索、固定ジョブの提案、証明、修正試行数、
チェックポイント、検証済み成果の公開先ブランチへの保存を選べる。
Pythonは選ばれた操作を実行し、実際のLean結果を返す。
Codexは実行器の実装・監視を担当し、次の数学補題を指示し続ける構造にはしない。

数学の目標・定理文・証明はDeepSeekが作成する。
ホストは定理文と元ノートの対応を点検し、最終目標を固定した。
証明本文はホストが手作業で編集しない。

## 固定した完了条件

[goal.json](../../../.agents/skills/deepseek-goal/goal.json) に、DeepSeekが作成した
2つの正確な定理文とSHA-256を保存した。

- `CFSmallDefectGoal.small_defect_curve_exclusion`：ノートのS=1..12の条件の下での曲線排除。
- `ThirtyCofactorGoal.thirty_cofactor_exclusion`：元の二項係数の式をそのまま使った30余因子の非存在。

どちらもCFの正しさ・証明書の健全性を仮定に入れていない。
型を弱める、既存証明を上書きする、補題数で完了判定する、モデルのPASSだけを採用することはできない。
両方の固定定理が実Leanで通り、標準公理依存のみで、GitHubへ保存済みの場合だけ `complete` にできる。
全四変数方程式の解決とは区別する。

## 実行と確認

リポジトリのルートから実行する。既存のキーとmax推論プロファイルを使う。

```bash
python3 docs/research/nested-binomial/v10_formal/deepseek_goal.py run
python3 docs/research/nested-binomial/v10_formal/deepseek_goal.py status
python3 docs/research/nested-binomial/v10_formal/deepseek_goal.py pause
```

`run` は保存状態を再開する。スキルは毎回読み、元の研究スキル・状態・参考資料もAPIヘルパーが読み込む。
過去の読取・検索結果は出典付きの作業メモリにも保持し、再開時にも復元する。
mathlib検索のglobはライブラリのルートから解釈し、ファイル一覧も取得できる。
数学的な次の指示をCodexへ求める必要はない。
`set_plan` でDeepSeekが依存関係付きの研究計画を保存できる。
計画の記載や自己申告から証明済みとは判定せず、実際のモジュール検査記録を別に表示する。
途中のチェックポイントでは継続し、上限・停止・実行エラーでは未完了のまま状態を保存する。
停止要求は現在の操作終了時に確認し、実行中の証明ワーカーは停止して成功済みの前半を保持する。
プランナーのAPI応答待ちは停止要求後も応答まで待つ場合がある。

既定の1回の実行上限は **6時間・48判断・API報告の出力合計200万トークン**。
プランナー、別呼び出しの範囲点検、子ワーカーの推論を同じ予算ファイルで集計する。
各呼び出しはmax、出力上限131072（推論込み）を基本とし、残り予算に合わせて上限を下げる。
修正試行はDeepSeekが1〜20回から選び、指定なしなら5回で一度結果を返して次の方針を考え直す。
不明なusageは無料扱いせず、その要求上限で計上する。
これはAPIが返した使用量の管理であり、請求額の保証ではない。

実行状態と非公開の生応答は `/workspace/.cloud-setup/deepseek-goal/nested-binomial-cf/`。
進捗の公開用要約は `DEEPSEEK_GOAL_PROGRESS.md`。
生の推論チャンクやAPIキーをGitHubへ保存しない。
環境停止中に動作し続ける常設サービスや、Mistralへのデプロイではない。

## 検証と保存

Leanの構文・API不一致・未解決ゴール・計算量上限などを分類し、
実際のエラー位置のソースと一緒にDeepSeekへ返す。失敗履歴は再開後も保持する。
純粋な計算量不足なら、同じソースのままheartbeatを40万から最大320万まで、
再帰上限を1024から最大4096まで段階的に増やす。全再試行で同じ180秒の期限を共有する。
構文や数学のエラーを伴う場合は、変更なしの再コンパイルを繰り返さない。
これらの上限は `v10_formal/deepseek_harness.json` に保存している。

未使用変数・未使用タクティクなどのlintは記録し、Lean exit 0・許可公理のみという
証明の合格条件とは分ける。実ログで警告だけで棄却されていたDeepSeekの証明を、
本文を変更せず再検査して通過を確認した。過去に受理した本文を優先して保持し、
回収した候補も固定型に対する再検査を必須とする。

`diagnose_job` は実ログと部分的な成功を返す。
`update_job_context` は固定した型を変えずに研究資料・mathlibソースを追加する。
`review_failure` は別呼び出しのDeepSeekから修正方針を受け取り、次のワーカーへ渡す。
同じモデルによる助言であり、独立査読や検証済み証明ではない。

固定ジョブの範囲は別のDeepSeek呼び出しで点検する。同じモデルであり、外部の独立査読ではない。
証明は既存の `deepseek_goal_worker.py` で実行・修正し、検証済みモジュールを
`goal_verified_modules.json` へ登録する。全体チェッカーは局所依存を順にコンパイルする。
保存は検証済みソース、固定ジョブ、検査記録、進捗要約だけを明示的にstageする。
無関係なstage済み変更があれば、それを混ぜてcommitしない。

保存先は既存の非公開PR #1の `research/nested-binomial-2026-11-05`。
通常のpush後にremote SHAを照合し、PRのmerge・環境公開・新しい公開サイトの作成は行わない。

別Codexも同じ研究ブランチを更新するため、保存前にそのブランチをfetchし、
両方の履歴を残すGit mergeで同期する。これは研究ブランチ内の同期であり、PRのmergeではない。
push中にremoteが進んだ場合は最大3回まで同期して再試行する。
検証済みLeanソース・固定goalを変更するremote更新は自動適用せず、
コンパイル入力が変わった場合は再検査を要求する。強制pushはしない。
保存直後に別のコミットが追加されても、保存したコミットがremoteの祖先であることを確認できれば保存成功とする。
回復不能なエラーは実際のGit診断を残してblockedで止め、同じ保存処理にモデル判断を消費し続けない。

## 数学研究の手法自体を研究する

DeepSeekが数学的戦略・形式化手順・証明書設計を仮説として提案し、実際の未完了部分で試す。
`inspect_methods` は実試行を集計し、`propose_method` で適用条件・手順・成功/失敗基準を記録する。
`use_method` で次の計画と固定ジョブへ適用し、`evaluate_method` で実測と本人の評価を保存する。
新しいジョブは選択中の手法を引き継ぐ。検証後に評価待ちの試行があればプランナーに表示する。

比較は同じ定理文のSHAと過去の基準履歴に結び付ける。受理済みseedの再検査は新証明に数えず、
中断やデータ欠測を数学的失敗、測定時間ゼロ、無料の試行とは扱わない。
候補応答のトークン表はプランナー・範囲点検・批評・最終レビューを含む総研究費用ではない。
逐次的な前後比較は統制実験ではなく、一般的・因果的な優越性の証明ではない。

`DEEPSEEK_METHOD_RESEARCH.json/.md` に仮説・実測・評価を保持する。
手法の提案や自己評価は、数学的証明、Lean通過、最終目標の完了を意味しない。
`.agents/skills/deepseek-research-methods/SKILL.md` はAPI呼び出しごとに読み込む。
研究の再開後も、適用した手法・固定型・基準履歴・結果ファイルのSHAを引き継ぐ。

圧縮された全証明書は、`read_research` で `.json.gz` を有限行だけ参照できる。
展開は8MiBが上限で、圧縮ファイルをそのままジョブの文脈へ渡すことは認めない。

APIの一時的な500/502/503/504/520には既存の有限再試行枠で対応し、
認証・クォータの失敗は再試行しない。再試行前に共有の終了時刻と残トークンを再確認する。
各Lean候補の実測をattempt_records.jsonへ逐次保存するため、
最後のモデルレビューが通信失敗しても候補の検証記録を失わない。
全モジュールの成功・保存には、固定型の再検査と通常のレビューを引き続き必要とする。

`github_status` は設定済みの研究PRとheadのcheck-runsを読み取る。
ユーザーはDeepSeekによるGitHub操作を明示許可済みで、保存・同期・PR要約更新に同じ許可を取り直さない。
GitHubのチェック結果と、固定Lean/mathlibでの数学的検証は区別する。
